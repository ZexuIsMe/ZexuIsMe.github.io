## 线程组

【线程数】 表示模拟的用户数量
【Ramp-Up】 模拟第一个用户到最后一个用户进场的时间，换句话说就是慢启动，从小到大的增长方式，**模拟用户 “非瞬间涌入” 的情况，避免因用户骤增导致系统虚假瓶颈**
【循环次数】 表示该线程执行的轮数
【调度器】 勾选后，可勾选"循环次数"的"永远"复选框，配饰持续时间，在该时间内无限次的执行线程

## 执行并发

    jmeter -n -t jmx文件 -l 日志文件 -e -o 报告文件

|   options    | DESC                     |
|:------------:|:-------------------------|
|      -n      | 以**命令行**的形式执行JMeter      |
|      -t      | 表示测试目标文件（.jmx）           |
|      -p      |                          |
|      -l      | 将测试结果保存到指定的文件中           |
|              | **必须是一个不存在的文件或是空内容的文件**  |
|      -j      |                          |
|      -e      | 表示测试完成后生成测试报告            |
|      -o      | 指定 HTML 报告的输出目录          |
|              | **必须是一个不存在的文件夹或是一个空文件夹** |

【日志文件】 必须是一个不存在的文件，运行时会主动创建
【报告文件】 必须是一个不存在的文件夹或是一个空文件夹，若文件夹不存在则在运行时会主动创建

## 关于 JSON Path

```json
{
  "data": 123,
  "list": [
    {"a": 1, "name": "张三"},
    {"a": 2, "name": "李四"}
  ]
}
```
> 绝对获取    

获取`data`：`$.data`

> 相对获取

获取`a`：`$..a`

> 按条件获取参数

获取`a`: `$.list[?(@.name=="张三"")].a` 

## Question：何为性能瓶颈？

**瓶颈**是性能测试领域中对于缺陷的描述，同样的缺陷的修复叫优化

## Question：性能瓶颈怎么定位的？

对JMeter命令行执行后产生的报告进行分析

初步分析错误模块提供的信息，大胆推测可能得问题所在拿出本次压测的日志信息，与开发一起讨论定位是瓶颈可能性，余下时间交给开发，测试从旁协助分析定位.

怎么个协助法呢？

比如初次定位下来，发现数据写入时会出现订单重复的情况，与开发讨论后，得出一个执行方案，该方案是先看看是否是因为SQL语句导致的，请求开发的协助，提供相关的业务流SQL语句。

而测试这边通过JMeter JDBC 做好前期的准备工作，比如数据库连接的配置，调试取样，结果数，以及CSV数据集的准备工作，将SQL语句按业务逻辑逐一写入 JDBC Request 中，再执行一定轮次的并发，比如模拟200个用户的操作，并循环10次，根据报告情况做分析下一步的目标。

通过这样的流程逐步排查定位瓶颈所在。

根据报告内容分析错误信息，配合开发分析定位目标代码，
比如发现是数据库写入数据时的错误，
那么将相关的SQL语句以及业务流摘出来，进行二次性能测试；
再通过二次测试报告缩小排查范围。

一般在这几个方面
硬件性能不够；
代码冗余或是代码复杂度高；
过多的复杂查询，比如四五张表的联查；
