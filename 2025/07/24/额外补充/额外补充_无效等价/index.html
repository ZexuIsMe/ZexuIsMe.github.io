额外补充_无效等价

粥记捣蛋 2025-08-13 21:31

软件测试 测试用例 额外补充 测试用例设计方法 无效等价类划分 软件测试 测试用例设计 无效等价类划分
  1. 1. 实操层面：用 “场景化清单” 控制测试范围
  2. 2. 总结：“度” 的本质是 “风险与成本的平衡”

Eg: 某银行APP，设计了一个查询密码，其需求为6位数字

Q：如题，你会如何设计？

A：用等价类划分法去设计，一个有效，两个无效。

错，还有一个无效等价类：非数字，而非数字又能延伸出多个新的无效等价类

此时，你可能会想，为什么需要做非数字的无效等价类划分，一般来说银行的APP有属于自己的数字键盘，何况根据功能而言，前端在做设计的时候，会根据需要只调用数字键盘的。

如果这样想，就会忽略掉一个很重要的信息：数据的重要程度。

除了前端做数字限制外，还需要考虑是否会被抓包，从而绕过前端直接进入后端的情况，需要验证后端是否做了相关的验证。

此时，你或许有了新的疑问：

Q：如果是这样的话，那么在做这样的输入框的测试用例时，都需要考虑到非目标主要条件、是否含有特殊字符、是否有特殊字符等等考量，那么这个度在什么地方呢？不能说每个能输入且调用API的地方都要做前后端的假象猜测来设计无效等价类吧

A：在输入框测试中，无效等价类的设计确实需要把握 “度”—— 既不能过度冗余（增加无效工作量），也不能遗漏关键风险（导致安全或功能漏洞）。这个 “度” 的核心判断标准是：基于场景的风险等级 + 系统架构的校验责任边界。

故此，如何做到有效的划分出无效等价类呢？
关键判断依据：明确 “校验责任边界” ，测试无效等价类的核心不是 “猜测漏洞”，而是基于系统架构的 “校验责任划分”：
• 前端校验：主要负责 “用户体验层”（即时反馈、减少无效请求），通常处理明显的格式错误（如长度、基础类型），但不依赖其作为安全屏障。
• 后端校验：负责 “安全兜底”，必须处理所有可能的无效输入（包括前端可能绕过的场景），尤其是敏感场景。

因此，无效等价类的设计需明确：

  • 该输入最终会被哪些系统 / 接口处理？
    若输入会进入核心业务系统（如银行的交易接口、支付系统），必须严格覆盖无效类；若仅在前端展示（如备注），可简化。
  • 是否存在 “绕过前端” 的可能性？
    能通过 API 直接调用（如后端接口无权限校验）、抓包修改参数、浏览器调试工具篡改输入等场景，必须覆盖后端校验的无效类。
    纯前端交互（如本地计算器输入），则只需验证前端逻辑即可。

实操层面：用 “场景化清单” 控制测试范围

为避免过度设计，可通过以下清单判断是否需要覆盖某类无效等价类：

  1. 输入内容是否涉及 “安全 / 资金 / 核心数据”？
    是 → 必须覆盖全量无效类（包括特殊字符、非目标类型等）。
  2. 后端接口是否对输入做 “强类型 / 格式约束”？
    例如：接口文档明确参数类型为 “数字”，则必须测试 “字符串、特殊字符” 等无效类型（验证后端是否严格校验）；若参数类型为 “字符串”（如用户名允许字母 + 数字），则无需测试 “非数字”。
  3. 是否有历史漏洞或行业常见风险？
    例如：银行系统曾因 “特殊字符注入” 出问题，或行业内有 “接口参数未校验导致 SQL 注入” 的案例，则需重点覆盖相关无效类。
  4. 测试成本与收益是否匹配？
    例如：一个内部管理系统的普通查询输入框，即使存在无效输入漏洞，影响也极小，此时无需过度测试；但面向公众的登录输入框，必须 “宁多勿漏”。

总结：“度” 的本质是 “风险与成本的平衡”

敏感场景（如密码、交易）：宁多勿漏，必须假设 “前端限制可能失效”，覆盖全量无效等价类（包括非目标类型、特殊字符等），核心验证后端校验。
非敏感场景：聚焦 “影响业务的核心无效类”（如长度超限、格式错误），前端校验逻辑为主，后端验证基础格式即可。

本质上，测试不是 “无差别猜测漏洞”，而是基于业务风险、系统架构和历史经验，针对性地设计无效类 —— 既确保核心场景的安全性，又避免为低风险场景浪费资源。
